# 项目开发闭环

## 明确需求

1. 读取根目录 `AGENTS.md`、工作区状态和相关代码，保护已有用户改动。
2. 提炼功能点、行为边界、接口、受影响文件、测试场景和验收条件。
3. 先自行检索仓库并用合理假设消除不确定性。只有缺失信息会改变公开接口、数据语义、兼容性、安全边界或主要实现方案时，才提出精简的阻塞问题并等待回答；说明已知事实、影响和需要的决定。
4. 用户明确只要求计划时，仅输出可执行计划，不修改文件。用户要求“先计划再实现”时先展示计划，然后继续执行，除非用户明确要求审批。其他情况不逐阶段暂停，持续完成实现与验证。

## 实现功能

1. 按确认的需求做最小范围修改，遵循现有架构、C++20 风格和本地抽象；需要新增目标时更新适当的 `xmake.lua`。
2. 为新增行为和修复补充或更新 Google Test，覆盖正常路径、边界条件和关键失败路径。不要为通过检查而削弱断言或改变既定需求。
3. 有对应项目脚本的操作必须调用脚本。脚本报告代码问题时修复业务代码；脚本确实缺少当前项目所需能力时，先把能力补入对应脚本，再使用脚本，禁止拼接一次性等价命令绕过。
4. 保持自主推进，直到需求完成或遇到需要用户授权、外部服务或关键选择的真实阻塞。

## 执行质量闭环

代码发生变更后，严格按以下顺序执行，不跳步：

1. `bash scripts/lint.sh --changed`
2. `bash scripts/compile.sh build`
3. `bash scripts/codeql.sh run`
4. `bash scripts/test.sh`

任一步失败时读取完整输出并定位原因：

- 业务代码或测试问题：修复后从第 1 步重新开始，确保四道门禁验证的是同一份最终代码。
- 脚本能力不足：先修改对应脚本，再从第 1 步重新开始；不得直接运行 clang-tidy、cppcheck、curl、打包命令或其他等价命令规避脚本。
- CodeQL 服务不可达：遵循 `scripts/codeql.sh` 的探测与询问流程，不自行实现另一套提交或解析逻辑。
- 外部环境导致无法继续：完成所有仍可安全执行的检查，记录失败命令、完整原因和未验证范围，不把未运行的门禁报告为通过。

不得使用行级过滤截断门禁输出。最终要求 lint 严格通过、编译 0 error/0 warning、CodeQL 0 critical/0 high、测试 100% 通过。

## 最终汇总

完成后用中文完整报告：

- 已实现功能及可观察行为；
- 新增和修改的文件及其作用；
- lint、编译、CodeQL、测试各自执行的命令与结果；
- 新增或更新的测试场景；
- 做出的关键假设、兼容性影响和风险；
- 未完成项、阻塞原因及明确的后续动作；没有未完成项时写明“无”。

不要用“完成”代替证据，也不要省略失败或未执行的门禁。
