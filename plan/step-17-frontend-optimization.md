> 基线技术栈：React 19、Vite 8、TypeScript 6、React Router 7、Zustand 5、Tailwind CSS 4、Vitest 4、Playwright 1.61。

## 一、背景与优化前审计结论

Step 15 已建立九个页面和基础 API 封装，但第一版主要完成了页面骨架，没有把接口契约、失败路径、移动端和浏览器验收闭环。2026-07-22 优化开始前的源码审计确认以下问题；这些内容用于解释本轮改动动机，不代表当前实现仍然存在同样缺陷：

1. 第一版前端使用 `FormData` 上传，后端实际要求请求体直接发送文件原始字节，并通过 `Content-Disposition` 读取文件名。该实现会把 multipart 包装一并写入分片，文件名还可能退化为 `unnamed`。
2. 当时后端只有根据扩展名推断 MIME 的逻辑，没有真正拒绝非音频类型。类型不明的文件仍会以 `application/octet-stream` 落盘。因此需要建立服务端白名单，不能把前端校验当作安全边界。
3. 第一版上传页没有扩展名、MIME、零字节和角色大小上限预检，没有 `accept`，也不展示后端返回的详细错误。
4. 当时上传队列依赖数组索引和陈旧状态，多批选择可能更新错项；上传期间加入的新文件会停在 `pending`；没有移除、重试和取消。
5. 第一版把后端数字角色按字符串声明，首次登录后的 VIP 导航和权限判断可能失效。
6. 第一版文件下载通过 `window.open` 直接访问受保护接口，不会携带 Bearer Token，实际可能得到 `401`。
7. 第一版桌面侧栏、顶栏和迷你播放器固定使用 `240px` 左偏移，移动端没有导航入口并存在内容遮挡。
8. 第一版 `/player/:id` 忽略路由参数；播放器页和布局同时挂载 `<audio>`，可能双重播放并争用进度状态。
9. 第一版多数异步页面不能稳定区分加载、空数据和失败，且页面会用通用 Toast 覆盖 API 返回的详细原因。
10. 优化前仓库虽然安装了 Playwright，但没有配置、E2E 用例和移动视口验收；原计划中的 E2E 完成状态与事实不符。

## 二、目标与边界

### 2.1 本轮目标

- 让上传协议与后端一致，并建立服务端最终校验、前端即时预检的双层边界。
- 让用户能在上传前看懂限制，在上传中控制队列，在失败后看到原始原因并重试。
- 修复角色、认证下载、认证恢复和播放器的关键契约错误。
- 让应用在 `390px` 到 `1440px` 视口内可导航、可操作、无横向溢出或固定栏遮挡。
- 统一核心页面的加载、空数据、错误、进行中和危险操作反馈。
- 建立可重复的 Vitest 门禁和部署后的 Playwright 桌面/移动浏览器验收。
- 更新所有受影响文档，使版本、接口、脚本、部署和测试说明与最终代码一致。

### 2.2 非目标

- 不在本轮新增后端尚未提供的用户管理 CRUD；`/users` 会如实标记当前能力，不伪装成完整管理页。
- 不重做音乐元数据模型、歌单排序后端或音频编解码。
- 不把真实 Docker/MySQL E2E 隐式塞入普通 `scripts/test.sh`，避免单元测试依赖外部服务。
- 不仅依据浏览器提供的 MIME 判断类型；扩展名规则是前端预检，后端仍是最终权威。

## 三、上传策略与接口契约

### 3.1 允许格式

本轮只允许后端能够识别并进入音乐库的九种音频扩展名，扩展名大小写不敏感：

| 扩展名 | 存储 MIME |
|---|---|
| `.mp3` | `audio/mpeg` |
| `.ogg` | `audio/ogg` |
| `.wav` | `audio/wav` |
| `.flac` | `audio/flac` |
| `.aac` | `audio/aac` |
| `.m4a` | `audio/mp4` |
| `.wma` | `audio/x-ms-wma` |
| `.ape` | `audio/x-monkeys-audio` |
| `.opus` | `audio/opus` |

规则：

- 服务端按规范化后的扩展名执行白名单，拒绝无扩展名和未知扩展名。
- 浏览器 MIME 只用于发现明显冲突；空 MIME 不阻止合法扩展名上传。
- 零字节文件直接拒绝。
- NORMAL 单文件上限默认 `10 MiB`，VIP 默认 `100 MiB`；等于上限允许，超过上限拒绝。
- 前端提示基于当前服务端默认配置，后端响应始终拥有最终裁决权。

### 3.2 请求格式

```http
POST /api/files/upload HTTP/1.1
Authorization: Bearer <token>
Content-Type: audio/mpeg
Content-Disposition: attachment; filename*=UTF-8''sample.mp3
Content-Length: <文件字节数>

<原始文件字节>
```

- XHR 直接执行 `send(file)`，禁止使用 `FormData`。
- 后端兼容已有 `filename="..."`，并新增 RFC 5987 `filename*=UTF-8''...` 解码，以支持中文和特殊字符文件名。
- CORS 允许 `Content-Disposition`，保证 `VITE_API_URL` 跨源开发模式可用。
- 上传成功使用独立 `UploadResult` 类型，不再误声明为完整 `FileRecord`。

### 3.3 服务端预检与失败清理

- 在分片落盘前完成认证、文件名、扩展名、零字节和已知 `Content-Length` 大小检查。
- 对被拒绝的请求只消费请求体，不计算文件哈希、不写分片、不写数据库，返回结构化 JSON 错误。
- 上传处理失败时释放 OpenSSL 哈希上下文；不把校验失败报告成泛化的解析错误。
- 返回状态：不支持类型 `415`、空文件或无效文件名 `400`、超限 `413`、未认证 `401`。

## 五、测试矩阵

### 5.1 上传规则

| 场景 | 预期 |
|---|---|
| `song.mp3`、`SONG.MP3` | 允许 |
| 合法扩展名且 MIME 为空 | 允许，后端最终校验 |

| NORMAL 恰好 `10 MiB` | 允许 |
| NORMAL 大于 `10 MiB` | 前端不发请求，后端绕过测试返回 `413` |
| VIP 恰好 `100 MiB` | 允许 |
| 中文、空格、引号文件名 | 文件名往返保持一致或给出明确拒绝原因 |

### 5.2 队列和错误

| 场景 | 预期 |
|---|---|
| 同名文件、多批加入 | 按稳定 ID 独立更新，不串进度 |

| 单项 `413/415/500` | 展示后端原始原因，其余队列继续 |
| 上传中取消 | XHR 中止，项目标记已取消，可重试 |
| Token 失效 | 清理会话并跳转登录，不重复 Toast |
| 部分成功 | 汇总成功数、失败数和取消数，不显示“全部成功” |
