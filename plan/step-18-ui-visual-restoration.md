# Step 18：Crystal Music UI 视觉还原计划

> 状态：计划中，尚未开始 UI 实现。
>
> 性质：前端视觉专项。恢复 Step 15 完整设计版本中 Crystal Music（翠澄·雨璃）的青绿玻璃态与毛玻璃视觉合同；不改变任何业务功能、接口或技术修复。
>
> 视觉依据：`61b6fee:plan/step-15-frontend.md`（2026-07-20 的完整设计版本）。当前工作树中的 Step 15 已被归档压缩，不能替代该历史视觉依据。
>
> 技术基线：[Step 17：前端体验与上传链路优化](step-17-frontend-optimization.md) 及其 [运行时回归修复计划](bugfix-step17-runtime-regressions.md)。其中已完成的技术修复、自动化覆盖和验收结果必须完整保留。

## 一、目标与问题定义

当前前端具备可靠的认证、上传、下载、播放、响应式和无障碍能力，但视觉已被收敛为中性表面、清晰边框和小圆角的管理工具风格。这与第一期明确的 Crystal Music 设计不一致。

本轮目标是恢复“雨后清晨，青绿澄澈”的音乐产品体验：浅绿环境画布承载半透明玻璃卡片，侧栏、顶栏和迷你播放器形成毛玻璃层，翡翠绿色用于品牌与操作强调，让文件、音乐、歌单、上传和播放器成为同一产品世界的一部分。

本轮不把第一期中的未实现业务诉求混入视觉重构。视觉还原不等于新增功能。

## 二、范围与不变边界

### 2.1 本轮范围

- 调整前端设计令牌、背景、色彩、字体、透明度、模糊、边框、阴影、圆角、间距和动画节奏。
- 重塑登录/注册、桌面与移动应用壳层、文件与音乐卡片、歌单、上传队列、通知、迷你播放器和全屏播放器的视觉构图。
- 在 `375px`、`390px`、`768px`、`1024px`、`1280px` 与 `1440px` 视口下验证视觉层次、文字可读性、固定区域和内容不遮挡。
- 为视觉实现补充必要的浏览器截图或样式回归断言，但不改变既有业务测试的行为断言。

### 2.2 明确不做

- 不改变 REST API、WebSocket、后端代码、数据库、文件格式规则、认证令牌、权限模型、路由地址、状态数据模型或类型定义。
- 不改变原始 `File` 请求体上传、`Content-Disposition` 文件名、前后端音频签名校验、上传队列调度、认证 Blob 下载/播放、Range 流播或播放器资源回收。
- 不新增全局搜索、文件视图切换、歌单排序、用户管理 CRUD、音乐元数据字段、播放队列规则或新的业务入口。它们属于功能需求，须另立计划。
- 不用视觉模拟掩盖未实现能力；例如没有后端支持的用户管理仍应如实呈现能力边界。

### 2.3 必须保留的 Step 17 基线

| 范围 | 必须保持的行为 |
|---|---|
| 认证与权限 | 数字/字符串角色归一化、会话恢复等待、受保护路由和 `401` 清理语义不变。 |
| 上传 | 原始文件字节上传、九种格式预检、大小/零字节限制、两路并发、追加、取消、重试、移除和逐项错误不变。 |
| 下载与播放 | Bearer 认证、Blob URL 生命周期、单一 `<audio>`、深链恢复、前后曲边界和播放错误处理不变。 |
| 响应式与无障碍 | 抽屉开关、遮罩、Escape、焦点恢复、44px 触控目标、`focus-visible`、减少动画和 `aria` 语义不变。 |
| 状态反馈 | 加载、空数据、错误、重试、危险操作确认、忙碌态和后端详细错误展示不变。 |

## 三、视觉合同

### 3.1 品牌与色彩

| 要素 | 目标值或表现 |
|---|---|
| 产品气质 | 雨后清晨、青绿澄澈；克制而有层次，不做通用后台面板。 |
| 浅色画布 | 以 `#F0FDF4` 与 `#ECFDF5` 构成柔和浅绿环境层，避免装饰性光球和噪声。 |
| 品牌色 | 主色 `#059669`，强调色 `#10B981` 与 `#34D399`，危险操作继续使用清晰的红色语义。 |
| 深色画布 | 使用 `#0A0F0D` 与 `#0F1A14` 的深绿层次，而不是中性灰黑后台。 |
| 字体 | Logo/展示标题使用 `Righteous`，正文使用 `Inter`；保留系统回退和现有文本可读性。 |

### 3.2 材质与组件语言

| 组件 | 视觉要求 |
|---|---|
| `glass-card` | 半透明表面、`12px` 背景模糊、浅色半透明边框、轻绿色投影、`16px` 圆角；不能继续表现为近乎不透明的白色管理卡片。 |
| `frosted-bar` | 侧栏、顶栏和迷你播放器使用更强的 `20px` 毛玻璃模糊与分层边界，固定时仍保持内容可读。 |
| 输入与按钮 | 玻璃输入框与翡翠操作按钮使用 `12px` 圆角；悬停只做轻微透明度或位移反馈，不牺牲可访问焦点。 |
| 状态组件 | Toast、菜单、歌单选择器、上传队列与错误状态使用同一材质和对比度规则，不出现嵌套的厚重白卡片。 |
| 音乐占位 | 保留不依赖新 API 的封面占位，但将其设计成可辨识的音乐视觉焦点，不使用空洞的通用图标块。 |

## 四、需要修改的前端区域

| 区域 | 预期修改 | 保留行为 |
|---|---|---|
| `frontend/src/index.css` | 重建设计令牌、环境背景、玻璃与毛玻璃工具类、圆角、阴影、排版与安全动画。 | 主题切换、焦点、最小宽度、减少动画和触控尺寸。 |
| `components/GuestLayout.tsx`、登录/注册页 | 形成带品牌层次的浅绿登录环境与玻璃表单。 | 表单校验、提交锁、错误文案、重定向与主题切换。 |
| `components/Layout.tsx`、`Sidebar.tsx`、`Header.tsx`、`ThemeToggle.tsx` | 将侧栏、顶栏、菜单抽屉和用户区域恢复为连续毛玻璃应用壳层。 | 路由、桌面侧栏/移动抽屉、焦点恢复、角色显示和登出。 |
| `FileCard.tsx`、文件列表/详情页、`Pagination.tsx` | 恢复有层次的文件卡片与数据页视觉，不把信息密度降为装饰。 | 下载、VIP 删除、详情跳转、分页、加载/空/错误/重试。 |
| `MusicCard.tsx`、音乐库/歌单页 | 让封面占位、曲目信息和歌单操作呈现音乐内容层次。 | 搜索、防旧响应、播放、加入/移除歌单、创建歌单与忙碌态。 |
| 上传页与 `Toast.tsx` | 将拖放区、队列、进度和状态消息纳入统一玻璃材质。 | 校验、队列调度、取消、重试、移除、汇总和辅助技术播报。 |
| `AudioPlayer.tsx`、播放器页 | 强化大封面区域、时间轴与底部迷你播放器的视觉关联。 | 原生音频元素、认证 Blob、单实例、音量、进度、队列与错误处理。 |

## 五、实施阶段

### 阶段 A：设计令牌与基础材质

1. 在 `index.css` 恢复浅绿/深绿画布、品牌色、字体、玻璃透明度、模糊、边框、投影和圆角。
2. 校准文字、图标、状态色与玻璃背景的对比度，确保浅色和深色主题均满足可读性。
3. 保留现有 `focus-visible`、减少动画和移动端最小触控尺寸；不通过降低透明度或移除焦点来换取视觉效果。

### 阶段 B：入口与应用壳层

1. 将登录和注册重构为品牌化的玻璃入口，但不改变表单字段、校验、提交或跳转。
2. 将桌面侧栏、顶栏和迷你播放器统一为连续的毛玻璃层；移动端沿用现有抽屉逻辑，仅调整视觉与排版。
3. 顶栏保持现有页面标题、用户、角色和退出行为；不在本轮添加没有实际查询能力的全局搜索交互。

### 阶段 C：内容页与音乐表达

1. 文件页、音乐库、歌单和上传页应用一致的玻璃网格、信息层级和状态样式。
2. 音乐卡片与播放器使用静态封面占位、色彩和排版建立内容焦点；不引入新的封面 API 或媒体数据依赖。
3. 上传队列、菜单和 Toast 避免层层嵌套卡片，长文件名、错误与进度必须在小屏完整可读。

### 阶段 D：响应式、无障碍与视觉验收

1. 在规定视口验证背景、固定侧栏/抽屉、顶栏、内容区、Toast 和迷你播放器无重叠、无横向溢出。
2. 使用键盘完成菜单打开/关闭、焦点恢复、表单输入、播放器操作和上传入口；玻璃材质不得降低焦点或文字可见性。
3. 补充稳定的视觉截图或关键样式断言，覆盖浅色、深色、桌面与移动关键页面；截图目录和报告名称继续使用时间戳。

## 六、验收标准

### 6.1 视觉验收

- 页面第一眼应呈现 Crystal Music 的浅绿环境、翡翠强调和层叠玻璃，而非中性白灰后台表面。
- 卡片、输入和按钮分别符合 `16px`、`12px`、`12px` 的目标圆角；卡片可感知半透明与背景模糊，导航和迷你播放器有明确毛玻璃层。
- `Righteous` 仅用于品牌和展示层级，正文保持 `Inter` 的扫描效率；长文本、错误和文件名不溢出或遮挡。
- 登录、文件、音乐库、歌单、上传与播放器的视觉语言一致，且全屏播放器与迷你播放器能被识别为同一体验。
- 浅色和深色主题均保持品牌色彩、可读文本、可见焦点和明确的危险/成功状态。

### 6.2 回归验收

- 所有现有前端单元测试、受保护路由、上传队列、下载/播放和部署 Playwright 用户流保持通过。
- 认证上传、授权下载、授权完整/Range 流播及容器健康检查继续覆盖，不因改样式而删除或弱化断言。
- 完成 UI 实现后，按仓库流程运行 `bash scripts/format.sh all`、`bash scripts/lint.sh --all`、`bash scripts/compile.sh build`、`bash scripts/codeql.sh run`、`bash scripts/test.sh`，并执行 Docker 四视口浏览器验收。

## 七、完成定义

只有同时满足以下条件，Step 18 才可标记完成：

1. 第一期开出的 Crystal Music 视觉合同已在当前前端可观察地恢复，且不再以 Step 17 的中性 `8px` 卡片规范作为视觉验收依据。
2. 所有 UI 改动限于视觉、布局和静态展示素材；路由、接口、数据模型、业务逻辑和 Step 17 技术修复没有被改变或回退。
3. 浅色、深色、桌面、平板和移动端关键页面均通过可读性、无重叠、无横向溢出、键盘焦点和固定区域验收。
4. 同一份最终代码通过完整质量门禁和部署后的四视口浏览器验收，且授权流播健康验证仍然通过。
